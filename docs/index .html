01

Abstract

Question: can a machine-learning model rank FlyRank content pages by refresh priority more reliably than a simple CTR-vs-position rule a content editor could apply by hand?

Data: this work is built on FlyRank's production search-performance warehouse — fact_content_daily_performance, 78,835,655 rows — worked through a March 2026 window (9,841,378 rows across 55 clients) and a 30,000-row anonymized modeling sample spanning 32 clients.

Method: a Random Forest classifier trained to flag declining content was benchmarked against a position-bucket CTR-gap rule, then validated two ways — a naive random row split and an honest client-grouped split — because the model's real job is scoring clients it has never trained on.

Result: the naive split reported ROC AUC 0.758 and Precision@50 0.90; the honest, client-grouped split dropped that to ROC AUC 0.610 and Precision@50 0.54 — statistically close to the 0.511 base rate, meaning the model does not yet show a measured edge over guessing at the top of the queue, let alone over the baseline rule.

What it's for: decision support only — the model and the rule can both seed a queue for a human editor to review, but neither is accurate enough, on this feature set, to rank pages unsupervised.

02

Introduction — the decision this supports

A FlyRank content editor manages hundreds of client pages at once. Every month, some of those pages are quietly losing search visibility — falling impressions, softening clicks — while most are stable. The editor can't manually re-check every page every month, so the real decision is: which handful of pages get a human look first?

Getting this wrong has two costs. Reviewing a page that's actually fine wastes an editor's limited hours. Missing a page that's genuinely declining means a client loses traffic for another month before anyone notices. Neither error is free, which is why a ranked, reason-coded queue — not a black-box verdict — is the right shape for this problem.

A single fixed rule ("flag anything trending down") ignores that normal click-through rates vary hugely by where a page ranks and what kind of content it is. A ranking model can, in principle, weigh several signals — position, click history, content age, engagement — at once. This paper tests whether it actually does, once evaluated honestly.

04

Methodology

Task framing. This is a ranking/scoring task: score each content page by refresh-worthiness so pages can be ordered from most to least in need of review. There's no ground-truth "needs refresh" label, so the target is a proxy: is_declining_label, set to 1 when a page's trend_direction is "down." A proxy, not an outcome — this is one of the honest limits in Section 06.

Baseline. A transparent rule: flag content whose observed click-through rate sits meaningfully below the average CTR of other content in the same search-position bucket, restricted to rows with at least 50 impressions so the gap isn't noise. The position-bucket signal behind this rule held up under testing — average CTR drops cleanly from 0.48% (positions 1–3) to 0.13% (positions 21+), a CONFIRMED signal.

Model. A Random Forest classifier (200 trees, max depth 10, min 25 samples per leaf, balanced class weighting) trained on 18 numeric features (log-scaled traffic and engagement aggregates, content age, position, CTR, scroll rate) and 8 categorical features (content type, intent, freshness tier, and similar), with trend_direction and trend_pct — the label's own source columns — explicitly excluded from the feature set.

Validation design — the part that matters most. The model was scored two ways on the identical data, features, and metric:

  • Naive split: a random 80/20 row split, stratified by label. The same client can appear in both training and test.
  • Honest split: a GroupShuffleSplit by client — a client's rows land entirely in train or entirely in test, never both. Confirmed: 0 client overlap.

The grouped split is the honest one because it mirrors the real use case: scoring pages for clients the model has never seen data from, not clients it partially memorized during training.

Naive — random row split
optimistic, misleading

Each colour is one client. The same client's rows land in both train and test — the model can partly memorize a client, then get "tested" on that same client.

Honest — client-grouped split
what this paper reports

Every client's rows stay on one side only. The red client in test was never seen in training — this is what actually tests generalization.

Leakage check. To confirm the evaluation harness itself was trustworthy, trend_pct — the label's direct source — was deliberately reintroduced as a feature. ROC AUC jumped from 0.610 to 1.000, exactly the signature of a leak. Removing it again confirmed the real feature set (Section above) contains no such leakage.

Reading it: the honest split's score (0.54) sits just above the base rate (0.51) — a small, not clearly meaningful, edge. The naive split's 0.90 was measuring the model's memory of clients it had already partly seen, not its ability to generalize.

Rewriting the claim, honestly. The bold version of this result — "Random Forest beats the rule-based baseline for flagging declining content" — was true only under the naive split. The safe, evidence-backed version: on held-out clients, the Random Forest score shows no measured advantage over the rule baseline at Precision@50; both sit close to the base rate. The model's random-split number reflected client memorization, not generalizable skill.

06

Limitations & honest framing

What this work cannot claim, stated before a reader has to ask:

01

No generalization advantage shown yet. Under honest, client-grouped validation, the model does not clearly outperform the simple rule or the base rate at the top of the ranked queue.

02

Proxy label, not ground truth. "Declining" is defined from a trend-direction rule, not a verified editorial outcome — the model may be learning to predict the proxy's own arithmetic rather than real refresh-worthiness.

03

Single month, no seasonality control. A genuinely seasonal page could be misflagged as declining during an off-season dip; this analysis can't tell the two apart.

04

Search Console coverage gap. Only 36.7% of rows in the working window have Search Console data — an access gap, not a random sample, so findings apply to connected clients only.

05

Modeling sample is a slice. The model was trained and evaluated on a 30,000-row, 32-client anonymized release, not the full 79M-row warehouse — results should be re-checked at full scale before any production use.

06

No page text. Content type is the only content-level feature; the model can point at which pages likely need a snippet rewrite, never suggest what the new title or meta description should say.

07

Ranked recommendations

Given the model shows no honest edge yet, the practical playbook leans on the simple rule — reason-coded, not just scored — as today's queue:

01

Ship the rule-based queue, not the model, today

The CTR-vs-position rule is simpler, equally honest under testing, and needs no retraining upkeep. Use it as this month's starting queue.

02

R1_HIGH_RANK_LOW_CTR → rewrite the snippet

Page ranks well (position 1–10) but CTR trails its bucket badly. The ranking work is done — the title or meta description isn't converting impressions into clicks.

03

R2_LOW_RANK_ADEQUATE_CTR → content/technical SEO review

CTR is fine for its position; the position itself (11+) is the ceiling. The snippet isn't the bottleneck — visibility is.

04

R3_LOW_VOLUME_UNRELIABLE → no action, re-check next month

Near the 50-impression floor — the CTR gap here is noise, not signal. Watch, don't act.

05

Keep a human in the loop, always

Never auto-publish a rewritten title or auto-flag a page to a client dashboard. A person confirms relevance and checks for active campaigns before anything ships.

06

Re-run monthly; watch for these retrain triggers

Re-check if next month's baseline error shifts more than ~10%, if the R1/R2/R3 mix shifts sharply, or if a page stays flagged for 2+ months after being actioned.
